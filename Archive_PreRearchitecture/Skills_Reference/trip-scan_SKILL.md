# Trip Scan

**Scope check first: this skill curates sources, it does not research places.** If a run of this skill starts producing "hidden gems," attraction write-ups, or itinerary content, that's out of scope — stop and redirect that output into the source-list format described below instead. A separate skill (built later) does the actual digging through these sources; Trip Scan's only job is deciding *which sources are worth digging through* and keeping that list growing.

## Why it's split this way
A small, high-trust, continuously growing list of sources is worth more over time than any one-off research pass. By keeping source curation as its own step, the list compounds — every destination scanned can turn up a new source that then benefits every future trip. Mixing curation with actual content research would bury that compounding asset inside one-off findings.

## Step 1 — Load the Knowledge Hubs index

Look for `Knowledge_Hubs.md` in the current project/working folder (e.g. the Trip Planner project folder). If it doesn't exist yet, create it there using a seed list of trusted travel sources as the starting content.

This file is the durable, cross-trip memory — it lives in the user's project folder (not inside the skill package) specifically so it survives and grows across sessions and destinations.

## Step 2 — Check the existing index against this destination

**First, prune proven-inefficient sources.** Read `Source_Efficiency.json` in the project folder (if it exists) — any domain there with `verdict: "low-efficiency"` gets **removed from `Knowledge_Hubs.md` outright**, not just skipped for this trip. A source that already cost more real mining time/tokens than it was worth on a prior trip doesn't deserve another chance to do the same thing again on this one or any future one — trip-master-plan is where that verdict got measured (Step 2b of that skill); this is where it actually gets acted on. Note briefly which sources were removed this way and why.

For each source still in `Knowledge_Hubs.md` after that, do a quick relevance check for the destination — enough to confirm the source actually has real content on this place, not enough to extract or summarize that content. A light search like `site:<domain> <destination>` or `<destination> <source name>` is sufficient. For Hebrew-language sources, phrase the check in Hebrew. **One search per source, snippet only — never `WebFetch` a source's page just to do this relevance check.** `Knowledge_Hubs.md` is a growing list (already 45+ sources); this check has to stay a fixed, cheap cost per source regardless of how large that list gets, or this step alone outgrows the whole stage's budget as the index compounds.

Sources that turn up nothing for this destination are simply left out of the destination's source list (Step 4) — no need to dwell on them, though it's fine to note briefly that they were checked and came up empty.

**Every remaining source needs an actual check — this step cannot silently sample the index.** A real run's `Sources.md` ended up with only 7 of `Knowledge_Hubs.md`'s 18 general-purpose (untagged) sources in `מקורות קבועים`, with the other 11 appearing in neither "Sources to use" nor "Checked, no relevant content" — meaning those 11 were never actually queried at all, yet the file still asserted `אין מקורות שלא היה להם כיסוי ישיר בסריקה זו` ("no sources lacked coverage"), which was false on its face once counted. Before writing Step 4's file, count every source still in `Knowledge_Hubs.md` after the low-efficiency prune and confirm each one lands in exactly one of the two lists — a source that's in neither was never actually checked, and the "nothing was rejected" line must never be written unless the "checked, no relevant content" list is genuinely empty *and* every single remaining source is accounted for in "Sources to use".

## Step 3 — Search for new sources and fold them in automatically

Search the open web for sources — independent blogs, forums, regional guides, niche subject-matter sites — that clearly have deep, first-hand, editorial-quality coverage of this specific destination and are not yet in the index. Hold these to the same bar as the seed list: a genuine point of view and real depth, not an SEO aggregator or generic listicle mill. **Hard cap: no more than ~10 web searches total for this step, and judge a candidate's depth from search-result snippets — at most one `WebFetch` of its actual page, only for a genuine finalist you're about to add.** Fetching every candidate's full page to judge it is exactly the kind of open-ended cost this pipeline has already been burned by elsewhere (see trip-master-plan's mining caps) — don't repeat it here.

No approval step needed — any source that clears this bar gets added straight into `Knowledge_Hubs.md` under the right category (or a new category if none fits), in the same one-line format as the seed entries, so it's indistinguishable from the original list in future scans. Be a reasonably strict judge here, since low-quality additions degrade the whole list over time — but don't hold up the process waiting for permission.

**This write to `Knowledge_Hubs.md` actually has to happen, not just get planned.** A real run added a genuinely-qualifying source to `<Destination>_Sources.md` (Step 4) but never wrote its line into `Knowledge_Hubs.md` at all — it existed only in that one destination's output, invisible to every future scan's Step 2 relevance check and permanently mis-classified as "new" if it ever got re-added, since there'd be no tag to check. Before finishing Step 3, re-open `Knowledge_Hubs.md` and confirm every source you're about to put in `<Destination>_Sources.md` as newly-discovered actually has a matching line in it — don't assume the write happened just because you drafted the line.

**If the destination name is an ambiguous English word or overlaps with something more famous (e.g. "Georgia" the country vs. the US state; this exact ambiguity has already wasted real search calls in a real run) — state the disambiguation explicitly in every search query and in any subagent prompt** (`"Georgia country Caucasus" not the US state`, or similar), instead of letting generic queries drift toward the wrong referent and burning calls sorting out irrelevant results.

## Step 4 — Write the destination source list

**`<Destination>` means the exact string used for the destination's folder and every other file in it — never a translated or anglicized version.** If the destination was entered in Hebrew (e.g. "גאורגיה"), every file this stage writes uses that exact Hebrew string as its prefix, even though the country's real name in English is "Georgia" and it's completely natural to think and reason about it in English while researching. This has caused a real, expensive failure: a subagent dispatched to do the actual source-checking reasoned about "Georgia" throughout its own work (correct — it's just internal reasoning) and then wrote its output file as `Georgia_Sources.md`, breaking the naming convention every other stage relies on. The next stage's `Read <Destination>_Sources.md` call then couldn't find its input, sending it into a confused, hours-long stall before it eventually errored out.

**Do Steps 2 and 3's actual searching yourself, directly in this main session — do not dispatch a subagent for it.** This whole stage (`stepA1-input-scan`) already runs on a cheap model end to end (invoked with `--model claude-haiku-4-5`), so unlike trip-master-plan's mining (whose main session runs on the default model and genuinely needs a subagent to reach Haiku pricing), dispatching a subagent here buys nothing on cost — and it has already cost real money to find out the hard way: a real run dispatched this via the Agent tool without an explicit `model` field, the subagent silently ran on the account's default (non-Haiku) model instead, and combined with an unbounded search budget it burned **$1.31 on what should have been a sub-$0.10 relevance-check pass** — more than double this entire stage's $0.5 ceiling, before a single output file got written. `subagent_type` alone does not select a model; a nested Agent call not given an explicit `model` field cannot be trusted to inherit this session's cheap one. Running the searches directly, in this same already-cheap session, removes that failure mode structurally instead of depending on remembering a field on every dispatch. It's also what avoids the anglicized-filename risk in the first place, since there's no subagent whose own English-language reasoning could leak into a file path — you're the one holding the correct destination string throughout, the same session that opened this prompt.

If Step 3's open-web discovery search still feels worth parallelizing on a particularly large trip, a subagent is allowed there **only** with `model: "claude-haiku-4-5"` explicitly set in that same Agent tool call — check the actual call you're about to make and confirm the field is present before sending it, don't rely on remembering it. Step 2's per-source relevance check against `Knowledge_Hubs.md`, being pure mechanical lookup, should just run in this session regardless.

Write `<Destination>_Sources.md` in the project folder: the combined, final list of every source relevant to this destination — both pre-existing ones confirmed relevant in Step 2 and newly added ones from Step 3 — each with a one-line note on what kind of coverage it has for this destination. This file is the handoff artifact: a separate research/itinerary skill reads it and knows exactly which sources to mine, without needing to rediscover any of this.

**Order the "Sources to use" list in two tiers, always:**

1. **`### מקורות קבועים (רלוונטיים לכל יעד)` first** — every relevant source that is *not* tagged with a `נוספה בסריקת <destination> (<date>)` note in `Knowledge_Hubs.md` (i.e. it's a general-purpose seed source, useful for any destination, not something a past per-destination scan added). These are the durable core of the list and belong at the top regardless of category.
2. **Everything else after, grouped into `###` subsections by source type** (e.g. blogs, hiking/trekking, wine/culinary, local/city-specific guides, sustainability) — the destination-specific sources, whether added on a past trip's scan or newly discovered by this one.

**Decide tier 1 vs. tier 2 by literally checking each source's own line in `Knowledge_Hubs.md` for that exact tag — never by how "general-purpose" its category heading there sounds.** A real run put a source under `### בלוגים ופורומים בעברית — כלליים` and left it out of `מקורות קבועים` reasoning that "general Hebrew blogs" belongs with the other blogs — but that source's `Knowledge_Hubs.md` entry had no `נוספה בסריקת` tag at all, meaning it's exactly the kind of always-relevant seed source tier 1 is for. `Knowledge_Hubs.md`'s own section headings (`## בלוגים ופורומים בעברית — כלליים`, `## טבע, הייקינג ומסלולים`, etc.) group sources by *topic* for that index's own upkeep — they say nothing about whether a given entry is general or destination-specific, and must not be used as a proxy for that. The same run also missed a source tagged only `נוספה:` with no `בסריקת <destination>` clause — that still fails to match the tier-2 tag pattern, so it's tier 1 too, even though its content (Caucasus-region trekking) reads as more narrowly regional than "any destination." Go source-by-source and check the actual tag text.

This ordering was missing on a real run — everything got grouped by type only, with general and destination-specific sources mixed together in the same subsection, making it hard to tell at a glance which sources are the trusted always-useful core versus this-destination finds.

```markdown
# Trip Scan — Sources for <Destination>
*Scanned <date>*

## Sources to use

### מקורות קבועים (רלוונטיים לכל יעד)
- Masa Acher (masa.co.il) — general travel content, destination articles; light Georgia coverage
- Jeepolog (jeepolog.com) — active forum threads on 4x4 routes; full content is login-gated, search snippets only
... (one line per general-purpose source relevant to this destination)

### הייקינג וטרקינג
- Wander-Lush (wander-lush.org) — newly added: Tbilisi-based writer, deep first-hand coverage of the Georgian Military Highway and lesser-known regions like Racha
... (one line per usable source, grouped by type)

## Checked, no relevant content
- 7 Worlds (7worlds.co.il), Hamizvada (hamizvada.com) — no destination-specific content found
```

Step 5's `Sources.html` card rendering must mirror this same two-tier, then-by-type grouping, **regardless of which rendering approach you pick.** Whether cards are static server-rendered HTML (`<div class="subsection-title">` markers between groups) or built client-side from a JS data array (`renderCards()` iterating a `sources` array), the same visible requirement holds: a header between each group, in the same order as `Sources.md`'s `###` headings, so the checkbox page reads identically to the markdown handoff file. **A real run using the JS-array approach flattened all 18 sources into one ungrouped list with no headers at all** — the two-tier requirement is about what the user *sees* on the page, not about a specific `<div>` class existing in the static HTML; if you choose the JS-array approach, group the array itself (or render multiple `<div class="subsection-title">` + card-container pairs, one per group, each populated from its own slice of the data) so the same visible grouping survives either way.

Do not include a "hidden gems," "findings by source," or any other content-summary section — that belongs to the follow-up research skill, not this one.

## Step 5 — Render the sources page, with real source selection, and update the dashboard

Every other stage in this pipeline updates the dashboard when it finishes — this one has to as well, even though it's easy to skip since Step 4 already produced a real file. This page is also where the user gets real control over what the next stage (trip-master-plan) is allowed to spend real research time and money mining — same philosophy as the Tab 4 map's checklist-and-confirm, applied one stage earlier.

1. Build `<Destination>_Sources.html`, one self-contained file (RTL, `dir="rtl"`, same visual language as the rest of the pipeline — cream/paper background, gold/accent color pair, card grid). Render every source from `<Destination>_Sources.md`'s "Sources to use" list as a card **with a checkbox, checked by default** (a source that already cleared trip-scan's own quality bar starts included — the user opts specific ones *out*, not the other way around). Each card shows the source name, its domain, and the one-line coverage note from Step 4. **The domain must be a real clickable `<a href="https://<domain>" target="_blank" rel="noopener">` link, not plain text — the user needs to actually open the source and look at it themselves to judge whether to keep it checked.** A real run rendered the domain as plain text with no `<a>` tag at all, silently dropping this even though it's a real requirement, not a nice-to-have — check the card markup you're about to write for an actual `<a href=...>` around the domain before moving on. Give a newly-discovered source (from Step 3) a visually distinct border/accent so it reads as new at a glance. Sources from the "Checked, no relevant content" list get their own section below, unchecked and disabled (nothing to select — they're informational only, listed so the user can see what was ruled out).

   **Also show a mining cost estimate on every card — this is meant to actively factor into the check/uncheck decision, not just sit there as trivia. Every card needs *some* actionable signal here — a bare "not measured yet" with no number and no tier is useless for deciding, and has already been flagged by the user as exactly that on a real run.** Read `Source_Efficiency.json` in the project folder (if it exists):

   - **Domain has a real entry** (`estimatedCostPerTripUsd` present — written by trip-master-plan's Step 2b after at least one real mining pass): show `💰 עלות משוערת לכריתה: כ-$0.59 (על סמך 2 טיולים קודמים)`, pulling `timesEvaluated` into the parenthetical. Add a small ✓ if `verdict` is `"efficient"` — this is exactly why a genuinely deep, higher-cost source can still be worth checking.
   - **Domain has no entry (never mined before) — the common case on a source's first appearance, and the case that must never be left blank.** Derive a qualitative tier from the coverage note you yourself just wrote for this card in Step 2/3, using it as a real, if approximate, cost signal instead of nothing: 🔴 **גבוהה יחסית** if the note signals deep/dedicated/extensive coverage (a whole blog devoted to the destination, "מעמיק," "מקיף," multi-year first-hand experience, detailed day-by-day guides) — such a source is likely to run the full three mining rounds, up to trip-master-plan's ~10-call-per-domain hard cap. 🟢 **נמוכה יחסית** if the note signals thin/generic/uncertain coverage ("כיסוי קל," "אם בכלל," a general-interest magazine with maybe one relevant piece) — likely to get only the one-page probe (per Step 2's probe rule) before mining moves on. 🟡 **בינונית** otherwise (partial mining, cut short by the diminishing-returns rule).

     **Attach an approximate $/trip range to each tier**, projected from the documented $0.015/mining-call heuristic (see `Source_Efficiency.json`'s `_readme`) against the typical call count each tier implies: 🟢 נמוכה יחסית ≈ **$0.02–0.04** (1–3 calls, probe only), 🟡 בינונית ≈ **$0.07–0.10** (5–7 calls, partial mining), 🔴 גבוהה יחסית ≈ **$0.10–0.15** (up to the ~10-call hard cap). These ranges assume the mining caps added to trip-master-plan are actually in force — they do not apply to any pre-cap historical figure (e.g. wander-lush.org's old $0.59/trip average, measured before that cap existed). State plainly next to the tier that this is a projection from a documented per-call cost assumption and the enforced call caps, not a real per-domain measurement — don't let the dollar figure read as more precise than that.

   Be upfront in the card copy itself (a small caption under the cost line, once per page is enough) that these are estimates — either derived from real call-count history or, for a first-time domain, a qualitative judgment call — never exact billing.

   **Also show a live running total of the CHECKED sources' cost estimates, updating on every checkbox toggle — not just a static per-card number.** Parse the midpoint of each checked card's `$X–Y` range (or the real `estimatedCostPerTripUsd` when present) and sum them into one line near the confirm button (e.g. `סה"כ עלות משוערת לכריתה: כ-$1.85 (16 מקורות נבחרו)`), recomputed on every `change` event on any checkbox. **This exists because a real run confirmed 16 sources with no visibility into what that added up to, and the resulting mining pass burned the entire $3 Part A budget with zero output** — trip-master-plan's per-domain call cap now scales down automatically as the confirmed count goes up (see that skill's Step 2), which keeps this from being a hard failure again, but the user should still be able to see the cost/coverage tradeoff *before* confirming, not discover it from a failed run afterward. The per-card ranges are the same static estimates either way (they don't need to know about the scaling); the running total is just their sum — simple to implement, and exactly the number that was missing when this failure happened.
2. **Confirm button, same wiring pattern as trip-master-plan's map:** near the top of the `<script>` block, define `const DESTINATION_NAME = '<Destination>';` and `const LOCAL_SERVER_URL = 'http://localhost:8787/confirm-sources';`. A prominent `אישור בחירת מקורות` button POSTs `{ destination: DESTINATION_NAME, domains: checked.map(c => c.domain) }` to that URL, then shows a plain-language result exactly like the map's confirm handler does: success (mentions the count, and that the next stage will pick this up automatically — no need to touch chat), a server-side error, or a connection-failure message pointing at `start_local_server.bat` (the `fetch` throws when nothing's listening on `localhost:8787`; that's the signal for that third case). This is the file trip-master-plan will treat as its real gate before mining anything — see that skill's Step 1.

   **If a card's domain is derived from its own `<a href>` link rather than stored on a data attribute, strip more than just the protocol.** A real run derived it via `anchor.href.replace('https://', '').replace('http://', '')` — reading the DOM `.href` property (not the raw attribute) always returns a fully-resolved URL, and browsers normalize a bare-domain URL to include a trailing slash (`https://masa.co.il` in markup becomes `https://masa.co.il/` when read back via `.href`). Every domain sent to `confirm-sources` ended up with a trailing slash as a result. Whatever extraction approach you use, also strip any path/trailing slash (e.g. take everything before the first `/` after the protocol) so the domains written to `Sources_Selected.json` are bare (`masa.co.il`, not `masa.co.il/`) and match `Sources.md`/`Knowledge_Hubs.md` exactly — don't rely on the next stage's own reasoning to paper over dirty data it was never supposed to receive.

   **The click handler must give immediate feedback and guard against double-submission — both are required, not cosmetic.** A real run had the button do nothing visible between click and the `fetch` resolving; the user, unsure the click registered, clicked again, and the second (genuinely later, since the server always writes a fresh `confirmedAt`) POST triggered a **second full A2 mining pass** queued right behind the first — real duplicate spend, not just a UI annoyance. On click: disable the button immediately, change its text to something like `⏳ שולח...`, and show a `pending`-styled status line before the `fetch` even starts (a module-level `inFlight` boolean guard as well, for belt-and-suspenders). On success, leave the button disabled (re-confirming the same trip isn't a real use case) and update the text to something like `✓ נשלח`. On failure, re-enable the button and reset the guard so the user can actually retry. Style `.result-message.pending` with `display: block` explicitly — the base `.result-message` rule defaults to `display: none`, so a pending state added without its own rule silently never shows.
3. Update `<Destination>_KESSLER_TRIP.html`'s Tab 2 block (between `<!-- TAB2:START -->` / `<!-- TAB2:END -->`) with `<iframe class="embed" src="<Destination>_Sources.html"></iframe>` — leave everything else in the dashboard untouched, same tab-update contract as every other stage.

Skipping this step leaves Tab 2 stuck on new-trip-input's "ממתין ל־..." placeholder forever, even though the actual source list exists on disk — this has happened in a real run, it's not a hypothetical.

## Notes

- If the destination isn't specified yet, ask for it before scanning anything.
- Keep the output genuinely short and scannable — it's a source list for another skill (or the user) to work from, not a report to read end-to-end.
- Be a strict judge on new sources (Step 3) — since there's no approval gate anymore, the quality bar you apply *is* the only quality control the list gets. When in doubt, leave a source out rather than pad the index.
- Don't do the next skill's job here — even if a search result surfaces an interesting specific place, that detail belongs in the destination source-list entry only as far as it justifies why the source is worth using, not as content to report on its own.
