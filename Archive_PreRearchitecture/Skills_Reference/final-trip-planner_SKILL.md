# Final Trip Planner

Stage 5 (last) of the KESSLER_TRIP pipeline: [[new-trip-input]] (Tab 1) → [[trip-scan]] (Tab 2) → [[trip-master-plan]] (Tab 4 map) → [[destination-showcase]] (Tab 3) → **this skill** (Tab 5, Tab 6, Tab 7). Everything upstream deliberately avoided sequencing a route or picking sleep bases so that this skill would have one clean, well-defined input: the set of points the user actually chose. This is the only skill in the pipeline that reads trip dates and duration as something to actively plan around, rather than just data sitting in Tab 1.

## Why the selection usually comes back through chat

`<Destination>_Route_Map.html` is a standalone page opened directly in the user's browser — not a Cowork artifact, and not something Claude has a live connection to by default. Historically there was no mechanism for its "confirm selection" button to hand that list back to Claude automatically, so the selection had to be described in chat. That's still the fallback, but it's no longer the only path: the confirm button now also POSTs the confirmed selection to a local helper server (`local_server.js`, started via `start_local_server.bat`) which writes it straight to `<Destination>_Selection.json` next to the map file — see Step 1.

## Part A — Resolve the confirmed selection

### Step 1 — Get the selection

**Check for a locally-written selection file first.** Look for `<Destination>_Selection.json` in the destination folder. If it exists (written automatically when the user clicked "confirm" on `<Destination>_Route_Map.html` while the local server was running), read it directly — it already lists exactly which point `id`s, `name`s, `category`s, and `region`s were kept, with a `confirmedAt` timestamp. Treat this as authoritative and skip asking in chat entirely, but do mention briefly which points/count were picked up so the user can catch a mistake.

If that file doesn't exist (the local server wasn't running, or the user described their pick straight in chat instead of using the button), fall back to chat: if the triggering message already names the kept points/regions, use that; otherwise ask directly which points from the Tab 4 checklist are staying in the trip. It's fine for the user to answer at the region level ("keep everything in the Karst region") mixed with point-level exceptions ("...but drop Lipica").

If both a `_Selection.json` file and a chat description are present and they conflict, the more recent one wins — say so explicitly rather than silently picking one.

### Step 2 — Cross-reference against the map's own data

Read `<Destination>_Route_Map.html` as a plain text file and pull the `REGIONS`/`POINTS` JavaScript array out of it directly (it's static, human-readable data embedded in the page — no need to run the page). Whether the kept-point `id`s came from `<Destination>_Selection.json` or from a chat description, match them against this same `POINTS` array and carry forward each point's `id`, `name`, `query` (geocoding string), `category`, `desc`, `source`, `url`, and `rec` flag — the selection file itself only carries the lightweight fields (id/name/category/region/rec/isSleep), so this lookup is still required either way to get the full description. This avoids re-typing or re-researching anything already captured upstream.

Also note, lightly, every point the user did **not** keep (just `name`, `category`, `query`, and which original region it came from — no need for the full description) — this becomes the "worth knowing about" list at the bottom of Tab 5 in Part D. Don't drop this data just because it wasn't selected.

Also read `<Destination>_Trip_Input.md` for the trip's date range, explicit day/night counts ("כמה ימים"/"כמה לילות" — use these directly for the day skeleton in Step 4 rather than re-deriving day count from the date range), participant count, and car y/n — this skill is the first one that actually plans around dates rather than just storing them.

## Part B — Sequence the trip into days

### Step 3 — Identify sleep-base candidates

Among the kept points, sleep-base candidates are: anything already tagged `Sleep` in the map data, plus any `City` point sitting in a region with several other kept points nearby. Aim for the fewest bases that still keep every day's driving reasonable (roughly under 1.5-2 hours one-way from a base to that day's points, when the map's own region-distance data or Directions results support that judgment) — don't force a new base for every region if two adjacent regions can share one.

**A base doesn't have to be one of the kept points.** If a cluster of kept points (e.g. a whole day-trip region like a cave/castle cluster) has no `City`/`Sleep`-tagged point among them, don't default to routing every day of that cluster back to a distant existing base just because that's what's already on the list — that produces exactly the wasteful pattern of driving to the same far-away city and back on multiple separate days. Instead, actively consider a real, findable town near that cluster as its own base, even if it wasn't one of the originally selected points (e.g. basing near Postojna for a Karst-region cluster rather than commuting there twice from Ljubljana). Stay within the destination's own country when doing this — proposing a base across an international border is a bigger decision (different rental-car/insurance terms, a different lodging market) that needs the user's explicit go-ahead, not something to decide unilaterally. If you're ever unsure whether an unlisted-but-better base crosses that line, ask rather than assume.

For a single-city destination (e.g. a 1-3 day city trip with no multi-region driving), it's normal and expected for there to be exactly one base (the city itself, or one hotel area within it) — don't force multiple bases where the trip only ever needed one.

### Step 4 — Build the day-by-day skeleton

Given the trip's total nights (from Trip Input) and the sleep bases from Step 3, assign nights per base roughly proportional to how many kept points cluster there, and order the bases to minimize backtracking (a simple geographic loop starting and ending near the arrival city beats zig-zagging). Produce a skeleton: `Day 1: <base>, arrival + these points`, `Day 2: <base>, these points`, etc. — every kept point must land on exactly one day.

This is a reasonable planning pass, not a promise of perfect optimization — note any judgment call that was non-obvious (e.g. "Bovec and Kranjska Gora share one base since they're 40 minutes apart").

## Part C — Write the day-by-day content

For each day, write:

- **זמן קימה (wake time)** — a sensible suggestion given that day's plan (earlier for a big hiking day, more relaxed for a city/travel day).
- **ארוחת בוקר (breakfast)** — usually "בבסיס הלינה," but call out a specific bakery/café if the Master Plan or a quick search surfaces a genuinely good one near that base.
- **תוכנית נסיעה (travel plan)** — the day's stops in visiting order, with driving/walking time between consecutive stops computed via the Google Maps Directions API (same client-side technique as trip-master-plan's map: stagger requests, compute Hebrew duration strings from the raw numeric value rather than trusting `duration.text`).
- **נקודות עניין (points of interest)** — the day's kept points, each with its carried-forward description.
- **מסעדות מומלצות (restaurant picks)** — 1-2 per day, genuinely relevant to that day's base/area. This needs a light, targeted web search **per base, not per day** — search once per unique base town and reuse that same result for every day at that base (a 3-night stay in one city means one search, not three) — a real, well-reviewed local place, not an invented one.

## Part D — Build Tab 5: the final route map + day plan

Produce `<Destination>_Final_Map.html`, one self-contained file, same visual language as `<Destination>_Route_Map.html` (RTL, same category colors) but scoped down: only the kept points get markers. Layout: map + sidebar, sidebar lists **"כל הימים" (all days) first, then Days 1..N** instead of regions.

**Default landing state is the all-days overview, not Day 1.** Geocode every kept point and fetch every day's driving directions up front (staggered), then show everything at once: every marker visible, every day's route drawn in its own distinct color (`google.maps.DirectionsRenderer` per day, `suppressMarkers: true`), and the map fit to bounds covering every kept point (so the whole geographic shape of the trip is visible — don't let this collapse into a tight zoom on whatever loaded first). The sidebar shows a compact per-day summary list (day number/label/date, its stops, its total drive time, color-matched to its route line) plus a trip-total drive time — this is what satisfies "see the roads and travel times for every day before drilling into one day's resolution." Only after the user clicks a specific day (or a summary row) does the view narrow: hide every other day's markers/route, fit tightly to that day's own bounds, and show that day's full detail card (wake time, breakfast, travel plan with drive times, points of interest, restaurant picks from Part C). A day view can always go back to the all-days overview via its own tab.

Carry forward every RTL/geocoding/marker lesson already documented in trip-master-plan's Part B (componentRestrictions by country code, never pass `label: null`, single shared InfoWindow, stagger Directions calls, compute Hebrew duration/distance strings from raw values, never put `dir="rtl"` on the map+sidebar page's `<html>` tag) — and trip-master-plan's newer lesson about region-highlight clicks never changing map zoom/pan applies here too: don't auto-zoom on anything but an explicit click.

**Clicking a point's name in the day's POI list must grow its marker, pan to it, AND open its info bubble** — the same three-part behavior trip-master-plan's map uses, not a stripped-down version. Register every kept point's marker and info-window HTML into a shared id-keyed lookup at geocode time (not just inside that marker's own click-listener closure) so a single `focusMapPoint(id)` function can be triggered identically from clicking the marker itself or from clicking its name in the sidebar list. This same `focusMapPoint` function should also be reused by the "worth knowing about" extra-places rows in Part D below — clicking one of those should feel identical (grow + pan + bubble), it's just that the marker for an extra point has to be geocoded lazily on that first click rather than existing already, since extra points aren't geocoded up front.

**Category breakdown pie chart.** Show a small pie chart (plain inline SVG, no charting library needed — a handful of `<path>` arcs computed from each category's fraction of 360°, same `CATEGORY_COLORS` used for markers) of the category mix (Nature/City/Attraction/Food, etc.): once for the whole final selection/route in the all-days overview, and once per day inside that day's card (only that day's own points). This is a quick visual sanity-check of whether a day or the trip as a whole is too one-note (e.g. all caves, no city time).

**Spaced-out principal schedule per day.** Beyond the existing wake/breakfast/travel/POI/restaurant fields, build an actual time-blocked timeline for each day: starting from that day's wake time (skip this entirely if wake isn't a fixed clock time, e.g. an arrival day keyed to a flight), add a breakfast block, then walk the day's `route` stop-by-stop adding a travel block (drive/walk time from the already-fetched Directions legs) followed by a visit block for any stop that's a real point of interest (not a bare base-return leg). **Round every computed clock time to the nearest half hour, and use clean 30/60-minute visit-duration estimates by category** (e.g. ~1 hour for a quick city stop, ~1.5 hours for a nature spot, ~2 hours for a bigger attraction) — this is a rough, principal-shape schedule, not a minute-precise itinerary, so there's no value in showing something like "14:37". Render each block generously spaced (not a cramped list) with a rounded clock time, an icon, and the block's label.

**Critical gotcha: fetch each day's travel legs one pair at a time, never as a single multi-waypoint Directions request.** A single `DirectionsService.route()` call carrying the whole day's stops as waypoints fails *as a whole* if even one leg has no route in the requested `travelMode` (e.g. one stop meaningfully far from the rest, or a body of water in the way) — `status !== 'OK'` then applies to the entire day, so none of that day's legs ever populate and the whole day's schedule is stuck on a permanent "computing real times" placeholder even though most of its legs were individually fine. This is exactly what happened in a real run (Milan): the timeline rendered with no travel times in it at all, for the whole day, because one request covering every stop failed outright. Fetch each consecutive pair separately (base→stop 1, stop 1→stop 2, …), staggered the same way the "worth knowing about" distance lookups already are — one bad leg then only blanks that single leg (fall back to a plain-language "זמן הליכה/נסיעה לא זמין" for it), not the rest of the day. Pick `travelMode` per leg from the trip's car y/n (Trip Input) and the leg's rough distance — `WALKING` for a compact same-city leg, `DRIVING` for anything between towns/regions or wherever a car was arranged — rather than hard-coding one mode for the whole day.

**A short, fun one-line intro at the top of every day's card.** Before the wake/breakfast/travel fields, add a brief, engaging sentence (with a fitting emoji) summarizing what that day is broadly about — this is what a person skimming the tabs actually wants to read first, before the logistics. Keep it light and specific to that day's actual plan, not generic filler.

**Lodging city at the end of every day.** Close out each day's card with an explicit, visually distinct line naming that night's lodging city (pulled straight from that day's `base`) — or, on the trip's final day, a clear departure note instead of a lodging line. This is the answer to "where do we sleep tonight" and should never be left implicit in the base-tag alone.

**Driving distances shown on the map itself, not just in the sidebar text.** Alongside each day's colored route line, draw a small distance label (a plain custom `google.maps.OverlayView` pill — no charting library — showing e.g. "18 ק"מ") at the midpoint of each leg (a straight-line midpoint between the leg's start/end location is a good-enough anchor; it doesn't need to trace the actual curved road). Toggle each day's labels on/off together with that day's markers/route, exactly like the existing marker and renderer toggling between the all-days overview and a single-day view.

**Critical gotcha: never write `class X extends google.maps.OverlayView` (or extend any other `google.maps.*` class) as a top-level statement.** The Maps script tag is loaded `async`/`defer`, so the page's own inline `<script>` block finishes parsing and starts executing before `google` exists on `window`. A class's `extends` clause is evaluated the instant the class statement runs — so a top-level class extending a Maps type throws `ReferenceError: google is not defined` immediately, which silently aborts every top-level statement that comes after it in that script block (while hoisted `function` declarations, including `initMap` itself, are unaffected and still get called later by the Maps callback). The visible symptom is confusing: the map, markers, and routes all look fine (because they're built inside `initMap`, called correctly), but anything relying on a `const` declared later in the same top-level script — e.g. `EXTRA_REGIONS` for the "worth knowing about" section — stays permanently uninitialized, so that section hangs on its loading placeholder forever, and the custom overlay (e.g. the distance labels) silently never appears since the class itself never got defined. Always define any `class ... extends google.maps.*` **inside** `initMap()` (or a helper called from it) — e.g. `let DistanceLabel; function defineDistanceLabelClass() { DistanceLabel = class extends google.maps.OverlayView { ... }; }`, called as the very first line of `initMap()` — never as a bare top-level class declaration.

**"Worth knowing about" section pinned at the bottom of the sidebar.** Using the not-kept points carried forward in Part A Step 2, render a persistent list (visible regardless of which day/overview tab is active) grouped by their original region, each row showing name, category dot, and driving distance. **Distance must be measured from the currently viewed day's own lodging base, not some fixed "nearest of all bases" figure** — "how far is this from where I'm actually sleeping tonight" is the useful question. So this section is day-aware: when a specific day is open, compute (or reuse a cached) distance from that day's `base` to every not-kept point; when the all-days overview is open (which spans multiple bases at once, so there's no single reference point), show a neutral prompt to open a specific day instead; on a day with no fixed lodging (e.g. the departure day), say so rather than showing a distance.

Use `DirectionsService` for this (one call per not-kept point, staggered — the same service already used for the day routes), **not** `DistanceMatrixService`. Distance Matrix is a separate Google API that may not be enabled on the destination's API key even when Directions/Geocoding/Maps work fine — a matrix call failing wholesale (every row silently reporting "distance unavailable") is a real failure mode to expect, not a hypothetical. Cache results per base name (not per day), since multiple days commonly share the same base (e.g. two days both based in the same city) — switching between those days should reuse the cached lookups rather than recomputing.

## Part E — Build Tab 6: the focused showcase

Produce `<Destination>_Final_Showcase.html`. Unlike destination-showcase (Tab 3), which curates a representative *subset* for inspiration, this page is complete by design — **every kept point gets a card**, since this is the actual trip, not a preview. Group cards by day (from Part B), so the page doubles as a visual index of the itinerary. Each card: photo (reuse destination-showcase's Wikimedia Commons hotlinking approach — no license/attribution tracking needed, same as Tab 3), name, the carried-forward 2-4 sentence description (no need to re-research what Tab 3/4 already captured), and a **"קרא עוד במקום" link** — a genuinely useful on-site deep-link for pulling up more detail once actually there (prefer a Hebrew or English Wikipedia article on the specific place if one exists, otherwise fall back to the source URL already captured in the map data). Same RTL/visual-tone conventions as destination-showcase.

## Part F — Build Tab 7: the booking checklist

Produce `<Destination>_Checklist.html`: an RTL HTML table, columns **✓ / משימה / תאריך מ / תאריך עד**. Rows:

- **טיסות הלוך ושוב** — dates from the trip's start/end (Trip Input).
- **מלון — `<base name>`** — one row per sleep base from Step 3, with check-in/check-out dates from the Step 4 skeleton.
- **רכב שכור** — only if Trip Input says the trip is with a car; dates span the full trip.
- **Per kept attraction that plausibly benefits from advance booking** — **filter before you search, don't search everything.** Skip the search entirely for anything that's obviously free/passive/walk-up by nature — a viewpoint, a neighborhood, a general nature walk, a market, a monument you just look at. Only spend a real search call (`<place name> advance booking` / `<place name> הזמנת כרטיסים מראש`) on points that plausibly need it by category or description: timed-entry sites, guided-tour-only attractions, named activities (rafting, paragliding, cable cars), and popular restaurants that take reservations. **Hard cap: no more than ~15 booking-check searches total for the whole trip**, regardless of how many kept points there are — if the filtered list is still longer than that, keep the ~15 most plausibly-bookable and skip the rest rather than searching all of them (note briefly which were skipped for being past the cap, not because they were judged unbookable). Only add a row when the search actually supports it — don't pad the checklist with attractions that just walk up fine. Date = the day it's scheduled for, from Part B.

Each row gets a real `<input type="checkbox">`. Since this file is a standalone page opened directly in the user's own browser (not a sandboxed Cowork artifact), persist checkbox state in `localStorage` keyed by destination + row id, so checked items stay checked across reloads — this is the one place in the whole pipeline where that's appropriate.

This is the pipeline's actual end — report back to the user with a short summary of the day plan (number of days, bases, point count) rather than continuing into anything further.

## Notes

- No license verification or attribution for Tab 6's photos — same personal-use-only rule as destination-showcase.
- This skill is the only one allowed to sequence a route, pick sleep bases, or reason about dates as something to plan around — that's the whole reason trip-master-plan drew its boundary the way it did. Don't second-guess or redo trip-master-plan's or destination-showcase's work; just consume their outputs.
- If the user's chat description of their selection is ambiguous (e.g. names a place that doesn't match anything in the map data), ask rather than guessing which point they meant.
- Keep the restaurant search genuinely light — once per day/base, not once per point. This isn't a food-guide skill.
- If a destination's dashboard was built before the 7-tab layout existed, this skill is responsible for migrating it (adding the two missing nav buttons and tab-content divs) rather than leaving it broken.
